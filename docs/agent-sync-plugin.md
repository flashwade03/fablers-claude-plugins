# Agent Sync Plugin Development Plan

## Purpose

Agent Sync is a plugin-distributed configuration synchronizer for developers who switch between Claude Code, Codex, and other coding agents in the same repositories.

The core problem is configuration drift. Each agent runtime has its own entry files, settings, hooks, subagents, skills, and planning conventions. When those files are edited by hand, they slowly diverge. Agent Sync should make one repository-level source of truth generate the runtime-specific files.

## Product Positioning

Agent Sync should be distributed as a plugin because the user-facing workflow lives inside agent tools:

- Claude Code users should run slash commands such as `/agent-sync check` and `/agent-sync apply`.
- Codex users should get equivalent commands or skills.
- Project hooks should warn when generated files drift from the source.

The implementation should not be locked inside one plugin runtime. The plugin should be a wrapper around a deterministic CLI/core package.

## Architecture

Use a three-layer structure:

1. `agent-sync-core`
   - Owns parsing, validation, file generation, drift detection, and adapters.
   - Exposes a CLI: `agent-sync init`, `agent-sync check`, `agent-sync apply`, `agent-sync diff`.
   - Has no dependency on Claude Code or Codex plugin APIs.

2. `agent-sync-claude`
   - Claude Code plugin wrapper.
   - Provides slash commands and optional hooks.
   - Calls the core CLI or imports the core package.

3. `agent-sync-codex`
   - Codex plugin or skill wrapper.
   - Provides the same command vocabulary where possible.
   - Calls the same core implementation.

This keeps the product portable. Future adapters for Cursor, Gemini CLI, Aider, or other tools should be possible without rewriting the synchronizer.

## Repository Source Of Truth

Each managed project should define one config file:

```yaml
# agent-sync.yaml
version: 1

source:
  instructions: AGENTS.md
  plansDir: docs/plans

targets:
  claude:
    enabled: true
    claudeMd: CLAUDE.md
    importAgentsMd: true
    settings: .claude/settings.json
    agentsDir: .claude/agents
    hooksDir: .claude/hooks

  codex:
    enabled: true
    agentsMd: AGENTS.md
    config: .codex/config.toml
    hooks: .codex/hooks.json
    agentsDir: .codex/agents
```

The config file describes intent. Generated files should contain a short marker comment so `agent-sync check` can identify managed files and detect manual edits.

## File Strategy

### Shared Instructions

`AGENTS.md` is the canonical instruction file.

Claude should consume it through a thin `CLAUDE.md` adapter:

```md
@AGENTS.md

## Claude Code

This file is generated by Agent Sync.
Claude-specific rules live here only when they cannot be expressed in AGENTS.md.
```

Codex should consume `AGENTS.md` directly where supported.

### Runtime-Specific Settings

Runtime-specific files remain runtime-specific:

- `.claude/settings.json`
- `.claude/settings.local.json` when intentionally local and ignored
- `.codex/config.toml`
- `.codex/hooks.json`

Agent Sync should generate only the files declared as managed in `agent-sync.yaml`. Local secrets and machine-specific files should not be generated unless explicitly opted in.

### Agents And Skills

Claude and Codex represent subagents differently:

- Claude agents are Markdown files with frontmatter.
- Codex agents are TOML files.

Agent Sync should start with a small common schema and generate both formats.

Example common agent definition:

```yaml
agents:
  tdd-test-writer:
    description: Write failing integration tests for TDD RED phase.
    tools:
      - read
      - write
      - shell
    prompt: ./agent-sync/agents/tdd-test-writer.md
```

The MVP should support only fields that can map cleanly to both runtimes. Runtime-specific overrides can be added later under `targets.claude.agents` and `targets.codex.agents`.

## Commands

### `agent-sync init`

Creates a baseline `agent-sync.yaml` for the current repository.

If `AGENTS.md` and `CLAUDE.md` already exist, it should:

- Detect whether they are identical copies.
- Recommend `AGENTS.md` as the canonical source.
- Generate a thin `CLAUDE.md` that imports `AGENTS.md`.
- Refuse to overwrite files unless `--write` or `--force` is passed.

### `agent-sync check`

Validates that generated files match the current source.

Use this in CI and pre-commit hooks. Exit non-zero when drift is found.

### `agent-sync apply`

Writes generated files.

It should print a concise summary of changed files and never touch unmanaged files.

### `agent-sync diff`

Shows what would change without writing.

This is useful before applying changes inside an agent session.

## Claude Plugin UX

The Claude plugin should provide:

```text
/agent-sync init
/agent-sync check
/agent-sync diff
/agent-sync apply
```

It can also include a `SessionStart` or `UserPromptSubmit` hook that runs a lightweight drift check and warns the user when generated files are stale.

The hook should be advisory by default. Blocking hooks can be added later, but they are risky because they can interrupt normal coding work.

## Codex Plugin UX

The Codex side should expose the same operations through whatever mechanism is most native:

- A skill for configuration synchronization.
- A command wrapper if Codex plugin commands are available.
- A hook that runs `agent-sync check` at session start or prompt submission.

Codex support should not require Claude Code to be installed.

## MVP Scope

The first useful version should support:

- `agent-sync.yaml`
- `AGENTS.md` as canonical instructions
- generated `CLAUDE.md` with `@AGENTS.md`
- generated `.claude/settings.json` from declared plugin/hook settings
- generated `.codex/hooks.json`
- `init`, `check`, `diff`, and `apply`
- drift detection for generated files
- one plugin package in this repository that wraps the CLI for Claude Code

Do not implement cross-runtime agent conversion in the first cut unless the schema is already clear. It is useful, but not required to solve the initial drift problem.

## Non-Goals For MVP

- Managing secrets.
- Editing user-local files by default.
- Supporting every Claude and Codex setting field.
- Automatically resolving conflicting manual edits.
- Building a hosted service.
- Supporting every agent runtime immediately.

## Suggested Location In This Repository

Add a new plugin under:

```text
plugins/agent-sync/
```

Suggested structure:

```text
plugins/agent-sync/
├── .claude-plugin/
│   └── plugin.json
├── README.md
├── commands/
│   ├── agent-sync.md
│   ├── agent-sync-check.md
│   └── agent-sync-apply.md
├── hooks/
│   └── hooks.json
├── package.json
├── src/
│   ├── cli.ts
│   ├── config.ts
│   ├── diff.ts
│   ├── generators/
│   │   ├── claude.ts
│   │   └── codex.ts
│   └── index.ts
└── __tests__/
    ├── init.test.ts
    ├── check.test.ts
    └── generators.test.ts
```

This repository already has plugin examples under `plugins/damascus`, `plugins/fablers-agentic-rag`, and `plugins/vibe-architecture`. Use those as local style references.

## Test Plan

Unit tests:

- Parse minimal and full `agent-sync.yaml`.
- Generate `CLAUDE.md` from `AGENTS.md` import mode.
- Generate `.codex/hooks.json` from a shared hook declaration.
- Detect drift when a generated file is manually edited.
- Preserve unmanaged files.

Fixture tests:

- Existing repo with duplicate `AGENTS.md` and `CLAUDE.md`.
- Existing repo with custom Claude-only section.
- Repo with Codex hooks but no Claude settings.
- Repo with no agent files.

CLI tests:

- `init --dry-run`
- `apply --dry-run`
- `check` success
- `check` failure with drift

## Open Decisions

1. Package manager: reuse the TypeScript/npm pattern from `plugins/damascus`, or keep the first version script-only.
2. Generated file marker format: HTML comment for Markdown, JSON metadata field for JSON, leading comment for TOML where valid.
3. Whether `agent-sync.yaml` lives at repo root or under `.agent-sync/config.yaml`.
4. Whether Claude plugin commands should call `npx agent-sync` or a bundled script path.

## Recommended First Milestone

Build the smallest Claude-distributed plugin that can normalize this exact project pattern:

1. Detect duplicate `AGENTS.md` and `CLAUDE.md`.
2. Convert `CLAUDE.md` into a generated adapter that imports `AGENTS.md`.
3. Add `agent-sync.yaml`.
4. Implement `check` and `apply`.
5. Add tests using a fixture based on the ShearMadness layout.

That milestone proves the core value without overcommitting to every runtime-specific setting.
